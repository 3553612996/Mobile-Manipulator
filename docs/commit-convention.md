# 提交规范

> 提交信息是写给三个月后的自己看的。判断标准很简单：**只看提交信息，能不能知道这次改了什么、为什么改。**

---

## 1. 格式

```
<type>(<scope>): <简述>

<正文，可选>

<脚注，可选>
```

- **首行不超过 50 个字符**，以中文计约 25 字
- 首行**不加句号**
- 正文每行不超过 72 字符
- 一次提交只做一件事

---

## 2. type

| type | 用途 | 示例 |
| --- | --- | --- |
| `feat` | 新增功能 | `feat(protocol): 帧解析状态机` |
| `fix` | 修 bug | `fix(motor): PID 积分饱和导致启动过冲` |
| `perf` | 性能优化 | `perf(vision): 后处理改 C++，单帧 38ms→6ms` |
| `refactor` | 重构，行为不变 | `refactor(serial): 抽出帧解析状态机` |
| `test` | 只改测试 | `test(protocol): 补 LEN 越界用例` |
| `docs` | 只改文档 | `docs: 补充 OTA 命令字` |
| `build` | 构建系统 | `build: 加入 arm-none-eabi 工具链文件` |
| `ci` | CI 配置 | `ci: 增加协议单元测试任务` |
| `chore` | 杂项 | `chore: 更新 .gitignore` |
| `revert` | 回滚 | `revert: 回滚 "feat(vision): ..."` |

**`refactor` 和 `feat` 的区别**：重构不改外部行为。如果重构之后功能变了，就不能叫 refactor——否则回看历史时会误判"这次改动是安全的"。

---

## 3. scope

| scope | 范围 |
| --- | --- |
| `protocol` | `shared/protocol.*`、串口帧 |
| `motor` | 电机、编码器、PID |
| `servo` | 六轴关节、舵机总线 |
| `safety` | 超时、过流、限位、急停 |
| `bootloader` | 引导、Flash 写入、跳转 |
| `base` | `robot_base` 包 |
| `arm` | `robot_arm` 包 |
| `vision` | `robot_vision` 包 |
| `speech` | `robot_speech` 包 |
| `task` | `robot_task` 包 |
| `bringup` | launch、参数、地图 |
| `docs` / `ci` / `build` | 对应类别 |

不确定时**省略 scope**，不要硬凑。

## 4. 好与坏

```
❌ 改了一下
❌ update
❌ fix bug
❌ 1
❌ 完成串口
```

```
✅ fix(protocol): CRC 计算漏了 LEN 字段，3% 帧被误判
✅ feat(motor): 编码器 4 倍频计数，速度测量分辨率提升 4 倍
✅ perf(vision): 输入分辨率 640→416，推理 42ms→18ms
✅ fix(servo): 插补步长未限幅，第 3 轴启动瞬间超调 12°
```

**差别在哪**：好的提交信息包含**现象或量化结果**。坏的信息只有"我动了哪里"。

## 5. 改参数时怎么写

参数调整是最容易写成一团的地方。要求：**列出生效项、给出效果**。

```
perf(motor): 重调速度环 PID，直行 2m 偏差 8cm→1.8cm

- 左轮 Kp 0.8 → 1.2
- 左轮 Ki 0.02 → 0.05
- 右轮同比调整（两轮特性不一致，右轮 Kp 取 1.15）

测试条件：空载、瓷砖地面、目标 0.3 m/s
```

有了"测试条件"这一行，三个月后换了地面发现对不上时，能立刻判断是参数问题还是环境问题。

## 6. 拆分粒度

**一次提交 = 一个可独立描述、可独立回滚的改动。**

拆分原则：

| 该拆 | 不该拆 |
| --- | --- |
| 改协议 + 改两端实现 | 一个功能拆成 10 个提交 |
| 修 bug + 加复现测试 | 一次提交改 20 个文件、跨越 5 个模块 |
| 重构 + 顺手的功能 | 把格式化和逻辑改动混在一起 |

**格式化单独提交**：`style: clang-format 全量格式化` 单独一个，否则真正的逻辑改动会淹没在几千行格式差异里。

---

## 7. 什么时候提交

**能编译、能跑就提交。** 不要攒到"功能全部完成"再提交——那通常意味着一次几百行的提交，出了问题是灾难。

半成品也可以提交，但要说明清楚：

```
feat(arm): 逆解初版，仅支持垂直抓取

TODO: 奇异点检查、关节限位剪枝
当前只验证了正上方抓取场景
```

`TODO` 明写出来，比假装完成更可信。

## 8. 分支模型

`main` 是基线，`develop` 是开发线。功能分支从 `develop` 拉，合回 `develop`。

| 分支 | 用途 | 规则 | 存活期 |
| --- | --- | --- | --- |
| `main` | 可烧录、可回滚的基线 | 只接受 `develop` 的合并和 `hotfix/*`，每次合入打 tag | 长期 |
| `develop` | 日常开发集成 | 功能、重构、文档都提交到这里，允许短暂编译不过 | 长期 |
| `feat/<scope>-<简述>` | 一个功能 | 从 `develop` 拉，合回后删除 | ≤ 3~5 天 |
| `fix/<scope>-<简述>` | 一个缺陷 | 同上 | ≤ 3~5 天 |
| `hotfix/<简述>` | 基线紧急修复 | 从 `main` 拉，修完同时合回 `main`（打 tag）和 `develop` | 按需 |

分支名用短横线小写，`<scope>` 与提交信息的 scope 一致；拿不准就省掉 scope。

**为什么不直接提交 `main`**：`main` 上每个提交都对应一块能烧进板子的固件。开发中的中间状态
（编译不过、只验证了一半）放在 `develop`，基线才能随时退回去复现问题。

**分支存活不超过 3~5 天**，写不完就先合并一个能编译的版本。

## 9. 版本号与标签

版本号遵循语义化版本 `主.次.修订`，唯一来源是仓库根目录的 `VERSION` 文件。

| 位 | 何时递增 | 本项目的触发条件 |
| --- | --- | --- |
| 主版本 | 硬件架构变更、通信协议不兼容 | 换主控、串口协议升到 v2 这类两端必须一起升级的改动 |
| 次版本 | 新增功能 | 完成一个里程碑条目，例如 M3 底盘闭环 |
| 修订号 | 修 bug | 只修缺陷、调参数，不新增接口 |

`0.x` 阶段接口还在变，主版本保持 0，靠次版本递进。

**版本号只在发布时改**：功能合入 `develop` 不动 `VERSION`，否则每次提交都要猜下一个号。

发布流程：

1. `develop` 上目标功能完成，Keil 全量编译 0 error 0 warning
2. 台架测试通过（`docs/testing.md` L3）
3. 把 `VERSION` 改成新版本
4. `git switch main && git merge --no-ff develop && git tag -a vX.Y.Z -m "…"`
5. 推 `main`、`develop` 和 tag
6. 从 `main` 构建、烧录，这一版就是基线

```bash
# tag 必须与 VERSION 一致，发布前先自检
test "$(git show vX.Y.Z:VERSION)" = "X.Y.Z" || echo "版本号与 tag 不一致"
```

**tag 的含义**：这个固件 + 这个 ROS 包 + 这个模型，是一起验证过能跑的。

固件代码暂时不引用 `VERSION`：等 M2 做协议与 OTA 时，由构建从 tag 生成版本头文件，
避免"文件里一份、代码里一份"改漏。

## 10. 禁止事项

- ❌ 提交不能编译的代码到 `main`
- ❌ 在 `main` 上直接提交功能（只能合入 `develop` 或走 `hotfix`）
- ❌ 让 tag 和 `VERSION` 不一致
- ❌ 提交密钥、密码、WiFi 配置（`*.secret`、`env`、`config/wifi.yaml` 已忽略）
- ❌ 提交数据集、录包、模型权重、编译产物
- ❌ 提交信息只写 "update" / "修改" / "fix"
- ❌ 把格式化改动和逻辑改动混在一次提交里
- ❌ 用 `git push --force` 覆盖别人的提交（个人仓库重写自己的历史可以，但要清楚后果）
