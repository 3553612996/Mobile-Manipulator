## 1. 概述

M2 的验收目标是**串口协议在真机上闭环**：上位机按协议 v1 下发命令，MCU 正确解帧、执行、回 ACK，并按周期上报状态；异常帧被丢弃而不是把程序带崩。测试分三层：

| 层 | 内容 | 覆盖 |
| --- | --- | --- |
| L1 | PC 单元测试 | 协议表、编解码、CRC、分发、ACK、去重、运动学、超时、按键 |
| L3 | 真机台架 | 链路、上报频率、使能、速度、断流、急停、清故障、拒绝非法帧 |
| 手动 | 上位机 | 遥测刷新、速度下发、急停按钮 |

测试工具是仓库内的两份代码，不含一次性脚本：

- `tools/proto_loop.py`：闭环自动测试（`--auto` / `--auto --move` / `--sim`）
- `tools/host_gui/`：上位机（Qt + pyserial），用于手动验证

**通过标准**：L1 退出码 0；L3 全部 PASS、0 帧 CRC 错误；只回 ACK 不算通过，必须看到随后的 `STATUS`/`ODOM`/`EVENT` 与命令语义一致。

## 2. 被测对象

### 2.1 固件

| 项目 | 值 |
| --- | --- |
| 主控 | STM32F103RCT6，Cortex-M3，72 MHz |
| RTOS | FreeRTOS（tick 1000 Hz，heap 8192，静态任务） |
| 串口 | USART3（PB10/PB11），115200 8N1，DMA1_Ch3 循环 256 B + IDLE 中断，环形缓冲 256 B |
| 编译 | Keil MDK ARMCC V5.06 update 7，**0 Error(s), 0 Warning(s)** |
| 尺寸 | Code 35500 B，RO 768 B，RW 516 B，ZI 21164 B |
| 烧录 | J-Link |

配套的 PC 端解析代码在 `tools/host_gui/protocol.py`，与固件共用同一份协议定义（`docs/protocol.md` 为唯一契约）。

### 2.2 台架

| 项目 | 内容 |
| --- | --- |
| 供电 | 7.4 V（2S，5C）电池，接入主电源 |
| 底盘 | 四麦轮 60 mm，减速比 1:90，**架空**（轮子悬空） |
| 机械臂 | 未接舵机总线 |
| 夹爪 | 未接 |
| 上位机 | Windows 11，CH340 USB-TTL，Python 3 + pyserial |

### 2.3 前提条件

- 电池电压高于 `APP_BATTERY_LOW_MV`（6.8 V），否则 `0x0401` 在启动时锁存，`MANUAL`/`IDLE` 不可达；

- 底盘架空后再加 `--move`。

## 4. 缺陷与修复

M2 联调期间发现并修复 5 个缺陷，全部有复现路径和验证记录。

| 编号 | 现象 | 根因 | 修复 | 验证 |
| --- | --- | --- | --- | --- |
| D1 | 闭环脚本约 300 ms 才拿到 ACK，偶发误报"无 ACK" | Windows 上 `read(n)` 在 `timeout>0` 时会攒满 n 字节才返回，而 50 Hz 上报流让间隔永远小于超时 | `proto_loop.py` 改为 `timeout=0` + `in_waiting` 轮询 | ACK 延迟降到约 4 ms |
| D2 | 电池低压锁存 `0x0401` 后，随后的断流不再上报 `0x0202` | `app_raise_fault()` 已锁存故障码就拒绝新码 | 新增 `protocol_fault_severity()`，按 WARN/ERROR/FATAL 仲裁，高优先级顶替、同级保留先到 | 真机断流 → 0x0202 通过；L1 增加级别表用例 |
| D3 | 下发速度后轮子不转，ODOM 恒为 0 | `bsp_motor_dual_pwm_set_enable()` 没有调用者，H 桥一直处于 coast，`set_duty` 只记录数值 | `service_chassis` 在使能/失能/急停时同步开关四路桥臂 | 轮子转动；L1 断言四路桥臂状态 |
| D4 | ODOM 速度饱和在 32767 mm/s | `platform_motor_get_encoder()` 返回累计计数，服务把它当单次增量 | 服务保存 `prev_counts` 做差 | 实测 289 mm/s（目标 200）；L1 增加"无新计数位置不变"回归 |
| D5 | 里程计距离偏大 8.3%，低压阈值在 7.4 V 电池上误触发 | 轮径按 65 mm 计算（22918 counts/mm）；阈值沿用 3S 的 10.5 V | 轮径改 60 mm（24828 counts/mm）；阈值改 6.8 V（3.4 V/节） | 距离比例正确；MANUAL/IDLE 可达 |

D1 是测试工具的问题，不是固件；但它的价值在于：**误报"无 ACK"会掩盖真正的协议缺陷**，所以同样按缺陷记录。

## 5. 架构分层检查

针对 `01_APP` / `02_Service` / `05_Middlewares` 做了一次依赖扫描，检查是否有跨层直接调用：

| 检查项 | 结果 |
| --- | --- |
| app / service / middleware 里出现 `HAL_*`、`FreeRTOS.h`、寄存器名 | 无（0 处） |
| app / service / middleware 里直接调用 `impl_*` | 无（0 处） |
| `03_Platform` / `04_Impl` / `06_BSP` 反向调用 `app_*` / `service_*` | 无（0 处） |
| CubeMX 生成的头文件（`stm32f1xx_hal.h`、`usart.h` 等） | 只出现在 `04_Impl/impl_mcu` |
| 相对路径 `../` 包含 | 无 |

结论：**没有违背分层解耦的跨层调用**。以下两处是文档与实际依赖的差异，需要说明而不是修复：

1. **`06_BSP` 包含了 `03_Platform/platform_mcu` 的头文件**（8 个文件）。实际物理依赖是 `06_BSP → platform_mcu（薄转发）→ impl_*_wrap → HAL`。`platform_mcu` 位于 BSP 之下，而 `docs/architecture.md` 写的单链 `03 → 04 → 06` 把这一层简化掉了，阅读时容易误解。建议在架构文档里补一句说明。
2. **`01_APP` 直接调用 `platform_bsp_battery/led/buzzer` 与 `platform_os_*`**。文档允许 app 依赖 Platform，所以不算违规；但若严格坚持"app 只碰 service"，电池、LED、蜂鸣器应各包一层薄 service。当前规模下不值得增加三层转发，保留现状。

另：`platform_mcu_*.c` 全部是对 `impl_*_wrap` 的转发，是有意的隔离层，代价是一次函数调用和两份声明，属于设计取舍，不是冗余。

### 6.1 功能边界

| 项 | 现状 | 计划 |

| 里程计标定 | 24828 counts/mm 由 13 线 × 4 倍频 × 90 减速比 / (π × 60 mm) 算出，未做 2 m 直行实测 | M3 标定 |

| 机械臂 | 舵机总线未接，`SET_ARM_JOINTS` 未做动作验证 | M8 |
| 电池采样 | 主电源断开时读数约 2.7 V（无有效输入），分压比未用万用表复核 | M3 连同低压阈值一起标定 |

### 6.2 测试稳定性

以下两类现象不改变 M2 结论，但必须记录下来，M3 继续观察：

1. **偶发 1 帧 CRC 错误。** 今日 4 次静态运行中 2 次各出现 1 帧（约 1/460），固件与上位机都正确丢弃并重新同步，后续帧不受影响。单独抓包 60 s（4923 帧）0 错误，30 s、20 Hz 带 ACK 的命令流 600/600 ACK、0 错误，未能稳定复现。倾向 USB-TTL 适配器在双向流量下的偶发丢字节，M3 换适配器/加屏蔽线后复核。
2. **断流检查窗口偶发漏判。** 4 次运行中 1 次未在 1 s 观察窗内看到 `0x0202`，复跑通过。计划把脚本改为直接等待 `EVENT(0x0202)` 帧，而不是轮询 `STATUS`。

这两项都不应通过放宽判定标准来"变绿"：CRC 一项保持 `0 帧` 的通过线，漏判一项记录在案。

## 7. 结论

1. 协议 v1 的组帧、解帧、CRC、ACK、SEQ 去重、上报频率在真机上全部符合 `docs/protocol.md`；
2. 异常帧（未知命令、长度错误、CRC 错、断流）均被正确处理，没有出现死机或越界；
3. 故障码按级别仲裁，低压不会掩盖通信超时这类更高优先级故障；
4. 分层约束成立，app/service/middleware 中没有跨层调用；
5. 5 个缺陷已修复并有回归覆盖。

**M2 判定：通过。** 进入 M3 底盘闭环（PWM + 编码器 PID + 里程计标定）。M3 必须先把开环 +45% 的速度偏差和两项标定（麦轮几何、计数/毫米）做实，否则里程计与后续导航都会建立在错误的尺度上。
