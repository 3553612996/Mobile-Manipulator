# 四轮电机死区与速度环整定记录

> **状态：架空台架已完成一轮整定（2026-10-29）。** 死区与增益都来自真机测量，条件见表；**落地（带负载）后需要复测**。选定值已回填为 `app_robot_config.h` 的编译期默认值，并通过 `PARAM_SAVE scope=0/1` 写进外部 Flash 的参数/标定区（第 6 节），上电时从 Flash 加载，Flash 空白或校验失败才退回编译期值。

---

## 1. 为什么先量死区

速度环外环给定的是轮速，输出是占空比（‰）。直流减速电机在低占空比下不转：桥臂压降、电刷接触压降、齿轮静摩擦叠在一起，占空比必须超过某个阈值转子才起转。这个阈值就是**死区**。

死区不处理会带来两个具体问题：

1. **低速不可控**：目标 30 mm/s 时 PID 输出的占空比可能整段落在死区里，轮子要么不动、要么一旦积分攒够就突然蹦出去，表现为爬行/顿挫；
2. **零速漂移**：停车后积分残量作用在死区边缘，轮子可能缓慢爬行。现有代码用 `SERVICE_CHASSIS_ZERO_SPEED_EPS_MM_S` 在零目标时清积分，只能压住一部分。

量出死区后，才谈得上要不要加前馈补偿（把死区折成占空比偏置）以及积分项的下限。

**死区不是一个确定的数。** 第一次单次扫描就碰到同一占空比一次转、一次不转：转子停在不同齿槽位置时静摩擦不同。所以本文区分两个定义：

| 名称 | 定义 | 用途 |
| --- | --- | --- |
| 单次起转 | 从静止起转，某一次尝试中出现运动的**最低**占空比 | 只用于了解物理边界，**不能**用来做补偿 |
| 可靠起转 | 从静止起转，连续 3 次尝试**全部**运动的**最低**占空比 | 前馈补偿、低速调度的下限依据 |

**注意**：死区和负载强相关。架空（轮子离地）量到的是"空载死区"，落地后起转需要更大占空比。本文记录的是架空值，落地后要复测一次，两者都保留。

## 3. 死区测量

### 3.1 命令

```bash
python tools/bench/wheel_tune.py --port COM7 deadzone --yes
# 单轮复测（改完线序、换电机后用）：
python tools/bench/wheel_tune.py --port COM7 deadzone --wheels A --yes
```

工具按以下顺序工作：

1. `SET_ENABLE(1)` 使能底盘；
2. 对每个轮子、每个方向，用 `SET_PARAM 0x30~0x33` 以 40‰ 步长从 0 加到 400‰，每档保持 0.6 s，占空比每 100 ms 刷新一次（固件 300 ms 过期）；
3. 判定起转：该档末尾 40 % 时间窗内的平均速度 ≥ 10 mm/s；
4. 在起转的那一档内二分 4 次，得到**单次起转**；
5. 从单次起转值开始每次 +5‰，每档从静止起转 3 次，直到 3/3 全起转，得到**可靠起转**；
6. 再以 400‰ 保持 1 s，记录满量程附近轮速，用于把占空比换算成轮速；
7. 全程用 `REPORT_WHEEL_DUTY` 回读实际写入的占空比，与下发值不一致时表格里能直接看出来；
8. 结束时 `SET_ENABLE(0)`。

单轮双向约 40 s，四轮约 3 min。

### 3.2 可用参数

| 参数 | 默认 | 含义 |
| --- | --- | --- |
| `--step` | 40 | 粗扫步长（‰） |
| `--max-duty` | 400 | 扫描上限，固件硬上限也是 400 |
| `--hold` | 0.6 | 每档保持时间（s） |
| `--threshold` | 10 | 判定起转的速度阈值（mm/s） |
| `--repeat` | 3 | 可靠起转的重复次数 |

阈值取 10 mm/s 是因为编码器在 10 ms 采样下约 4 mm/s 一分度，低于这个数分不清"真在转"和量化抖动。

**判读**：

- 四轮可靠起转在 **67~100‰**，即满量程的 7~10 %；补偿量不大，但对 60 mm/s 以下的目标速度（≈ 105‰）来说占了一半以上，低速必须考虑；
- 同一轮正反向不对称最大的是 C（+82 / −80 与单次值 82/60）和 D（+80 / −100），D 反向偏高 20~25‰。目前不影响控制，但**D 轮的减速箱/联轴器值得检查一次**（同样的占空比下它需要的力矩更大）；
- 各轮在 400‰ 的轮速几乎一致（227~240 mm/s），说明四个电机和编码器标定没有明显个体差异；
- 方向一致性单独验过一次：±150‰ 下四轮都是"正占空比 → 正轮速"（A +77/−80、B +66/−75、C +75/−77、D +74/−76 mm/s），没有一路反号；
- 可靠起转处速度 21~42 mm/s，说明越过死区后轮速上升并不陡，低速段不需要特殊处理。

## 4. 速度环整定

### 4.1 顺序

1. **先 Kp**：Ki = 0、Kd = 0，Kp 从 0.5 起按 ×1.5 递增，直到阶跃响应开始超调或振荡，取振荡前一级的 70 %；
2. **再 Ki**：在上一步 Kp 下加 Ki，目标是稳态误差 < 5 %，Ki 加到误差达标且不明显增加超调为止；
3. **Kd 保持 0**：10 ms 采样速度做微分主要是放大量化噪声，除非后续给速度加滤波，否则不开。

### 4.2 命令

```bash
# 单组增益，四轮一起测
python tools/bench/wheel_tune.py --port COM7 step --speed 200 --hold 6 --yes

# 增益扫描：Kp 三档、Ki 两档（交叉组合，共 6 组）
python tools/bench/wheel_tune.py --port COM7 step --speed 200 --hold 6 \
    --kp 3.0 5.0 7.0 --ki 5.0 6.0 --yes

# 只测一个轮子
python tools/bench/wheel_tune.py --port COM7 step --wheels A --speed 200 --yes
```

工具以 50 Hz 下发 `SET_VELOCITY(vx=目标, wz=0)`，记录固定时长的 `REPORT_WHEEL_SPEED`，逐轮算：

| 指标 | 定义 | 目标 |
| --- | --- | --- |
| 稳态 | 最后 0.8 s 的平均轮速 | — |
| 误差 | (稳态 − 目标) / 目标 | **< 5 %** |
| 上升时间 | 达到稳态值 10 %→90 % 的时间 | < 0.3 s |
| 超调 | (峰值 / 稳态 − 1) | < 15 % |
| 纹波 | 最后 0.8 s 内峰峰值 | < 40 mm/s |

直行时四个轮子目标相同（逆解 `vx=200, vy=wz=0` 时四轮都是 200 mm/s），所以同一组增益下四轮指标可以直接横向比较。

**保持时间要够长**：积分项按 10 ms 逐拍累加，Ki = 0.6 时误差收敛的时间常数约 3 s。第一次只测 2 s，四轮"稳态"全是 −47 %，看起来像稳态误差，实际是还没收敛。本文所有结论都基于 **4~6 s** 的记录窗口。

## 5. 低速与死区补偿（已实现，按轮可配）

4.5 的结果里 60 mm/s 稳态误差 −2 % 左右，超调 30 % 但没有振荡，本身已达到 < 5 % 目标。补偿仍然实现了，原因是**低速起转**：目标 30 mm/s 时 PID 输出可能整段落在死区里，轮子要么不动、要么积分攒够后蹦一下。

实现形式是"只在静止时抬底"：

```text
if (目标 != 0 && |实测| <= 5 mm/s)
    duty = max(duty, +死区_正向)     /* 目标为正 */
    duty = min(duty, -死区_反向)     /* 目标为负 */
```

与"持续前馈 `pid_out + sign(target) * deadzone`"的区别：轮子转起来之后不再抬底，环路可以自由把占空比压到补偿值以下去减速，否则表现为刹车变慢、低速跟不住。

- 位置：`service_chassis_apply()` 闭环分支、`service_chassis_pid_duty()` 限幅之前；
- 数据来源：参数/标定区每轮一组 `deadzone_fwd/rev`（`0x54~0x5B`），编译期默认值取 3.3 的可靠起转（A 75/67、B 67/75、C 82/80、D 80/100），已随 `PARAM_SAVE scope=1` 落盘；
- 关闭方式：把某轮的值写 0，该轮就不补偿；
- **落地后必须复测死区再改这组数**——负载会让可靠起转明显变大，用架空值做补偿会补偿不足。

## 6. 回填与固化

### 6.1 选定值

| 参数 | 编译期默认（`app_robot_config.h`） | 整定值 |
| --- | --- | --- |
| `APP_CHASSIS_LEFT_PID_KP` | 5.0 | **5.0** |
| `APP_CHASSIS_LEFT_PID_KI` | 6.0 | **6.0** |
| `APP_CHASSIS_LEFT_PID_KD` | 0.0 | 0.0 |
| `APP_CHASSIS_RIGHT_PID_KP` | 5.0 | **5.0** |
| `APP_CHASSIS_RIGHT_PID_KI` | 6.0 | **6.0** |
| `APP_CHASSIS_RIGHT_PID_KD` | 0.0 | 0.0 |

四轮相同；`service_chassis_cfg_t` 的按轮数组（`pid_kp[4]` 等）保持"左两组、右两组"的填充方式即可。起转占空比的编译期默认值同为实测值（`APP_CHASSIS_DEADZONE_FWD/REV_PERMILLE`，A 75/67、B 67/75、C 82/80、D 80/100）。

**`SET_PARAM` 只写 RAM，掉电或复位就回到"上次保存的值，没有保存则回到编译期值"**；要让整定结果活过断电，必须再发一次 `PARAM_SAVE scope=0`（见 6.2）。标定类参数（轮径、四轮比例/方向/起转占空比）同样通过 `PARAM_SAVE scope=1` 固化。复现方式：

```bash
python tools/bench/wheel_tune.py --port COM7 step --speed 200 --kp 5.0 --ki 6.0 --yes
```

（`step` 会先下发增益再测量，等于一次"应用 + 复测"。）

### 6.2 写外部 Flash（已实现）

存储分区、记录格式与保存命令见 [flash-layout.md](../architecture/flash-layout.md) 和 [protocol.md](../architecture/protocol.md) 5.5 节。当前固件的行为：

1. `SET_PARAM` 写增益成功后在 RAM 生效（控制任务下一个 10 ms 节拍推入速度环），并置"参数脏"标志；
2. 主机发 `PARAM_SAVE scope=0` 后由 `appStorage` 任务写入参数区 60 B blob（擦写只有一个写者，不占控制任务）；
3. 上电时从 Flash 读参数，校验版本/长度/范围失败或空白则退回 `app_robot_config.h` 的编译期值；
4. 写成功后 `REPORT_STORAGE`（`0xC8`）的 bit0"无脏数据"置位，主机才知道可以断电。

固化时把 6.1 的四个值写进参数区，并把 `app_robot_config.h` 的编译期初值同步改成同一组数——编译期初值是 Flash 空白/损坏时的兜底，两者不一致会让"掉参数"故障表现得像正常工作。

## 7. 已知限制

| 限制 | 影响 | 处理 |
| --- | --- | --- |
| 死区是架空测量值 | 落地后起转占空比偏大 | 落地后按 3.1 复测，两套值都记录 |
| 增益也在架空条件下整定 | 带负载时积分可能偏快 | 落地后按 4.2 复测 60 / 200 / 300 mm/s 三档 |
| 死区有随机性（齿槽位置） | 单次测量不可重复 | 用"可靠起转 3/3"，复测时保持同一判据 |
| 电池电压会改变死区 | 满电/亏电表现不同 | 每次测量记录 `battery_mv`（本次 7.81 V） |
| 速度反馈是 10 ms 差分 | 单分度约 4 mm/s，纹波下限 | 不要用低于 40 mm/s 的目标评估 PID 好坏 |
| 增益不持久化 | 断电/复位丢失 | 见 6.2，固化实现前用 `step` 命令重新下发 |
| 测试占空比上限 400‰ | 无法测满转特性 | 400‰ 已给出 227~240 mm/s，满量程按线性外推 |
| 实测上报 40 Hz 而非 50 Hz | 每次阶跃只有约 160 个样本 | 脚本按时间戳计算，不影响结论；后续单独排查调度周期 |
| GUI 与台架脚本争用串口 | 打不开 COM 口 | 测前关闭上位机 |
