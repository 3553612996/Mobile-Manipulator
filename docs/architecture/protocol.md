# 串口通信协议 v1

RK3566（Host）↔ STM32F103RCT6（MCU）之间的应用层协议。

- 状态：**v1 草稿，实现中**
- 变更规则：任何改动同时修改本文档与两端代码，在同一个提交里

---

## 1. 物理层

| 项目 | 取值 | 说明 |
| --- | --- | --- |
| 接口 | UART | 3.3V TTL，TX↔RX 交叉，**必须共地** |
| 帧格式 | 8N1 | 8 数据位、无校验、1 停止位 |
| 波特率 | 115200（调试）/ 921600（正式） | 先用 115200 调通，稳定后再提 |
| 流控 | 无 | 靠应用层重发保证可靠 |
| 角色 | RK3566 = Host，STM32 = MCU | Host 主导指令下发，MCU 周期上报 |

**为什么先 115200**：波特率越高，线长和干扰越敏感。调试阶段报文短、频率低，115200 足够；等协议逻辑验证完再提速，能把"协议 bug"和"信号完整性 bug"分开排查。

## 2. 帧格式

```
偏移   0      1      2      3      4      5 .. 2+LEN   3+LEN  4+LEN
     ┌──────┬──────┬──────┬──────┬──────┬───────────┬──────┬──────┐
     │ 0xAA │ 0x55 │ LEN  │ CMD  │ SEQ  │  PAYLOAD  │ CRC_L│ CRC_H│
     └──────┴──────┴──────┴──────┴──────┴───────────┴──────┴──────┘
      帧头1   帧头2   长度   命令   序号    负载(N)      CRC16 小端
```

| 字段 | 长度 | 说明 |
| --- | --- | --- |
| HEAD | 2 | 固定 `0xAA 0x55`，用于在字节流中定位帧起点 |
| LEN | 1 | **CMD + SEQ + PAYLOAD** 的总字节数，即 `2 + N`。不含帧头和 CRC |
| CMD | 1 | 命令字，见第 5 节 |
| SEQ | 1 | 序号，0~255 循环，用于应答匹配与去重 |
| PAYLOAD | N | 负载，0 ≤ N ≤ 64 |
| CRC16 | 2 | 对 `LEN + CMD + SEQ + PAYLOAD` 计算，**小端存放**（低字节在前） |

**总帧长** = `5 + LEN`，最短 7 字节（空负载，如 ESTOP），最长 71 字节（负载 64 字节）。

### 为什么没有帧尾

帧尾（如 `0x55AA`）不携带额外信息——CRC 已经能判定帧的有效性，长度字段已经能定界。多一个帧尾只会增加字节数和出错面。**帧头用双字节**是为了在字节流里可靠地重新同步；一旦同步上，靠 LEN 就够了。

### LEN 的合法范围

`2 ≤ LEN ≤ 66`（CMD 1 + SEQ 1 + PAYLOAD 0~64）。**下限是 2 而不是 3**：ESTOP 没有负载，`LEN = 02`，把下限写成 3 会让急停帧被当成非法帧丢弃。超出范围的帧直接丢弃并回到等待帧头状态——这能挡掉大部分因错位导致的连锁解析错误。

## 3. 数值编码

| 类型 | 编码 | 范围 |
| --- | --- | --- |
| 线速度 | `int16`，单位 **mm/s** | ±32.767 m/s |
| 角速度 | `int16`，单位 **mrad/s** | ±32.767 rad/s（±1877 °/s） |
| 关节角度 | `int16`，单位 **0.01°** | ±327.67° |
| 位置 | `int32`，单位 **mm** | ±2147 km |
| 电池电压 | `uint16`，单位 **mV** | 0~65.5 V |
| 温度 | `int8`，单位 **°C** | -128~127 |
| PID 参数 | `int32`，实际值 ×1000 | — |

**统一用小端序**（低字节在前）。两颗芯片都是小端，理论上可以直接内存拷贝，但**不要依赖这一点**——显式按字节序列化和反序列化，代码才能在 PC 上跑单元测试。

**为什么用定点数而不是 float**：
1. 两端浮点实现可能有细微差异（虽然都是 IEEE754，但除法舍入在某些编译器优化下会不同）；
2. 传输体积小，解析快；
3. 定点数的精度是确定的，调试时看报文就能直接换算，不用手算浮点。

## 4. 命令字分配

| 区间 | 用途 |
| --- | --- |
| `0x01 ~ 0x3F` | 下行命令（Host → MCU） |
| `0x80 ~ 0xBF` | 对应命令的应答，值为 `CMD \| 0x80` |
| `0xC0 ~ 0xFF` | 主动上报（MCU → Host） |

## 5. 命令定义

### 5.1 下行命令

| CMD | 名称 | PAYLOAD | 长度 | 周期 | 需 ACK |
| --- | --- | --- | --- | --- | --- |
| `0x01` | SET_VELOCITY | `int16 v` (mm/s), `int16 w` (mrad/s) | 4 | 50 Hz | 否 |
| `0x02` | SET_ARM_JOINTS | 6 × `int16` 目标角 (0.01°) | 12 | 按需 | 否 |
| `0x03` | SET_GRIPPER | `uint8 action` (0=张开 1=闭合), `uint8 force` (0~100) | 2 | 按需 | 是 |
| `0x04` | SET_ENABLE | `uint8` (0=失能 1=使能) | 1 | 按需 | **是** |
| `0x05` | SET_PARAM | `uint8 id`, `int32 value` | 5 | 按需 | **是** |
| `0x06` | ESTOP | 无 | 0 | 事件 | **是** |
| `0x07` | CLEAR_FAULT | `uint16 code`（`0xFFFF` = 清除全部） | 2 | 事件 | **是** |
| `0x08` | PARAM_SAVE | `uint8 scope` | 1 | 按需 | **是** |
| `0x09` | PARAM_RESET | `uint8 scope`, `uint8 confirm` | 2 | 事件 | **是** |
| `0x0A` | STORAGE_QUERY | 无 | 0 | 按需 | **是** |
| `0x0B` | LOG_EXPORT | `uint8 source`, `uint8 action`, `uint32 from_seq` | 6 | 事件 | **是** |
| `0x0C` | CRASH_READ | `uint8 slot`, `uint8 flags` | 2 | 事件 | **是** |
| `0x0D` | LOG_CLEAR | `uint8 source`, `uint8 confirm` | 2 | 事件 | **是** |

**SET_VELOCITY 不需要 ACK**：它 50Hz 周期发送，下一帧自然就是重传，加 ACK 只会让带宽和状态机复杂化。可靠性由"超时停车"保证，而不是由重传保证。

**SET_ENABLE / SET_PARAM / ESTOP 需要 ACK**：这些是状态变更，丢了会出问题（比如失能指令丢了，机器人还在动）。

**存储类命令（`0x08~0x0D`）需要 ACK 且 ACK 只表示"已受理"**：擦除一个 4 KB 扇区最长 400 ms，如果等写完再回 ACK，通信任务会被阻塞，200 ms 指令超时会误触发。所以 ACK 在命令入队时返回，真正的落盘结果由 `0xC8 REPORT_STORAGE` 的 bit0（无脏数据）和 bit3（保存失败）体现。主机必须看到 bit0 置位再断电。

### 5.2 应答

`CMD = 原CMD | 0x80`

| 字节 | 字段 |
| --- | --- |
| 0 | `uint8` 被应答的 SEQ |
| 1 | `uint8` 结果码 |

结果码：

| 值 | 含义 |
| --- | --- |
| `0x00` | 成功 |
| `0x01` | 参数越界 |
| `0x02` | 当前状态不允许（如未使能时下发给关节） |
| `0x03` | 未知命令字 |
| `0x04` | 执行失败（如关节超限） |
| `0x05` | 忙：上一次存储写入或日志导出尚未结束 |
| `0x06` | 存储不可用：外部 Flash 未识别或分区表校验失败 |

### 5.3 主动上报

| CMD | 名称 | PAYLOAD | 长度 | 周期 |
| --- | --- | --- | --- | --- |
| `0xC1` | REPORT_ODOM | `int32 x_mm`, `int32 y_mm`, `int16 theta` (0.01°), `int16 vl` (mm/s), `int16 vr` (mm/s) | 14 | 50 Hz |
| `0xC2` | REPORT_ARM | 6 × `int16` 实际角 (0.01°), `int16` 夹爪位置, `uint8` 夹爪状态 (0=张开 1=夹持 2=夹空) | 15 | 20 Hz |
| `0xC3` | REPORT_STATUS | `uint8` 状态字, `uint16` 故障码, `uint16` 电池 mV, `int8` 温度, `uint16` 最大调度抖动 µs | 8 | 10 Hz |
| `0xC4` | REPORT_EVENT | `uint16` 故障码, `uint32` 时间戳 ms | 6 | 事件触发 |
| `0xC5` | REPORT_HEARTBEAT | `uint8` 状态, `uint16` 运行计数 | 3 | 10 Hz |
| `0xC6` | REPORT_WHEEL_SPEED | 4 × `int16` 实测轮速，顺序 FL / FR / RL / RR (mm/s) | 8 | 50 Hz |
| `0xC7` | REPORT_WHEEL_DUTY | 4 × `int16` 本周期实际写入电机的占空比，顺序 FL / FR / RL / RR (‰) | 8 | 50 Hz |
| `0xC8` | REPORT_STORAGE | 存储状态字与寿命计数，见 5.5.5 | 24 | 应答 `0x0A` 或保存结束时 |
| `0xC9` | REPORT_LOG | 一条日志或故障事件记录，见 5.5.6 | 15+N (N≤49) | 导出期间 ≤ 20 Hz |
| `0xCA` | REPORT_CRASH | 崩溃现场的一个数据分片，见 5.5.7 | 7+N (N≤57) | 应答 `0x0C` 后连续发 |

**REPORT_WHEEL_DUTY 与 REPORT_WHEEL_SPEED 同拍发送**（同一个 20 ms 节拍，先速度后占空比）。主机调参工具靠这一对数据判断"我下发的占空比固件到底写没写进去"：只有速度没有占空比时，一个被限幅或被拒的指令看起来和"电机不动"完全一样。占空比以满量程 1000‰ 计，带符号；底盘失能时全部为 0。

**REPORT_EVENT 只在事件发生时发一次**（故障产生、清除、模式切换）。周期性数据不要用它，否则 Host 侧要去重。事件帧丢了怎么办：Host 侧靠 REPORT_STATUS 里的当前故障码兜底，所以事件帧本身不需要重传——**状态是权威的，事件只是通知**。这是一个刻意设计。

状态字节（REPORT_STATUS 第 0 字节、REPORT_HEARTBEAT 第 0 字节，定义在 `protocol_def.h`）：

| 值 | 状态 | 含义 |
| --- | --- | --- |
| 0 | INIT | 上电初始化，尚未进入控制 |
| 1 | IDLE | 已就绪，未使能，电机不出力 |
| 2 | MANUAL | 已使能，接受 Host / 按键的运动指令 |
| 3 | AUTO | 预留：由 MCU 内部任务自主运动 |
| 4 | ESTOP | 急停锁定，需 `CLEAR_FAULT` 后重新使能 |
| 5 | FAULT | 有故障码锁存，具体码见第 8 节 |

**状态与故障码分开**：状态表示"现在能不能动"，故障码表示"为什么不能动"。Host 不需要从状态字反推故障类型。

### 5.4 参数表（SET_PARAM 的 id）

| id | 含义 | 单位 | 落盘区域 |
| --- | --- | --- | --- |
| `0x01` | 轮距 | mm | 标定区 |
| `0x02` | 轮径 | mm | 标定区 |
| `0x03~0x05` | 左轮 PID Kp/Ki/Kd（兼容别名：同时写 A 左前 + C 左后） | ×1000 | 参数区 |
| `0x06~0x08` | 右轮 PID Kp/Ki/Kd（兼容别名：同时写 B 右前 + D 右后） | ×1000 | 参数区 |
| `0x10` | 控制指令超时 | ms | 参数区 |
| `0x11` | 最大线速度 | mm/s | 参数区 |
| `0x12` | 最大角速度 | mrad/s | 参数区 |
| `0x20~0x22` | A 左前轮 PID Kp/Ki/Kd | ×1000 | 参数区 |
| `0x23~0x25` | B 右前轮 PID Kp/Ki/Kd | ×1000 | 参数区 |
| `0x26~0x28` | C 左后轮 PID Kp/Ki/Kd | ×1000 | 参数区 |
| `0x29~0x2B` | D 右后轮 PID Kp/Ki/Kd | ×1000 | 参数区 |
| `0x30~0x33` | A/B/C/D 轮开环测试占空比（台架专用，见下） | ‰ | **不落盘** |
| `0x40` | 日志等级（0=DEBUG 1=INFO 2=WARN 3=ERROR） | — | 参数区 |
| `0x41` | 死区补偿开关（0=关 1=开） | — | 参数区 |
| `0x50~0x53` | A/B/C/D 轮编码器比例 `counts_per_mm` | ×1000 | 标定区 |
| `0x54~0x57` | A/B/C/D 轮正向可靠起转占空比 | ‰ | 标定区 |
| `0x58~0x5B` | A/B/C/D 轮反向可靠起转占空比 | ‰ | 标定区 |
| `0x5C~0x5F` | A/B/C/D 轮方向（`+1` / `-1`） | — | 标定区 |

PID 增益范围：Kp/Ki `0..10000`（0.000~10.000），Kd `0..5000`（0.000~5.000）。**写入前必须校验范围**，越界返回 `0x01` 而不是静默截断——静默截断会导致调参时"改了没反应"，非常难查。

**`SET_PARAM` 只写 RAM 并置脏标志，落盘要单独发 `PARAM_SAVE`**。这两个动作必须分开：台架调参时一秒能改十几次，每次都擦 Flash 会把参数区写坏；而且擦除最长 400 ms，夹在控制指令流里会触发 200 ms 超时。分区与记录格式见 [flash-layout.md](flash-layout.md)，参数区与标定区的分界也按上表的"落盘区域"列：**"恢复出厂"只清参数区，标定区必须保留**。

`0x01`/`0x02`/`0x50~0x5F` 属于标定，写入前要求底盘失能（`scope=1` 的 `PARAM_SAVE` 同样要求失能），避免行进中改轮径/方向导致里程计跳变。

> **实现状态：已实现。** 固件 `app_handlers.c` 的 `app_handle_set_param()` 处理上表全部 id（`0x03~0x08`、`0x20~0x2B` 的 PID 队列、`0x30~0x33` 台架占空比、`0x40` 日志等级、`0x01/0x02/0x10~0x12/0x50~0x5F` 运行时标定与限速）。写标定 id 时若底盘已使能或急停锁定返回 `0x02`；越界值返回 `0x01`；RAM 写入成功后由控制任务在下一个 10 ms 节拍推入 `service_chassis`，所以 ACK `0x00` 表示"已存 RAM、已排队"，随后可用 `PARAM_SAVE` 固化。`0x10~0x12`（超时与限速）允许在使能状态下写，且只重载限速、不重置 PID 积分；`0x41`（死区补偿总开关）**尚未实现**，返回 `0x01`——当前用 `0x54~0x5B` 每轮独立设置，写 0 即关闭该轮补偿。
>
> **轮径与编码器比例的关系**：写 `0x02` 时固件按 `counts_per_mm = 4680 / (π · d)` 重算四轮比例（4680 = 13 线 × 4 倍频 × 90 减速比），因此**先写轮径、再写 `0x50~0x53` 的单轮微调**；反过来会丢失微调。取值范围：轮距/轴距 50~2000 mm，轮径 10~500 mm，`counts_per_mm` ×1000 为 1000~100000，起转占空比 0~1000‰，方向只能是 ±1，超时 10~5000 ms，最大线速度 10~500 mm/s，最大角速度 10~1500 mrad/s。完整范围表见 `app_params.c` 顶部的 `APP_PARAMS_*_MIN/MAX`。

#### 开环测试占空比 `0x30~0x33`

量电机死区必须能"绕过速度环、只给一个占空比"，否则速度环会把死区补偿掉，量到的永远不是电机本身的特性。

| 项目 | 规定 |
| --- | --- |
| 取值 | `-400 ~ +400` ‰，越界返回 `0x01` |
| 前置条件 | 底盘已使能且未急停；否则返回 `0x02`（BAD_STATE） |
| 失效 | 每轮单独计时，**300 ms** 内没有刷新就按 0 处理，该轮滑行 |
| 退出 | 任何 `SET_VELOCITY`、`STOP`、`SET_ENABLE(0)`、`ESTOP` 都立刻退出测试模式 |
| 方向 | 带符号；负值即反转，H 桥两个方向的死区通常不对称，两个方向都要量 |

进入测试模式时四轮占空比先清 0 并清空速度目标，只允许被写入的那一轮转动。测试模式期间 200 ms 指令超时不生效（它有自己的 300 ms 过期），所以主机可以只发测试占空比而不发速度指令。写入后固件在同一个 20 ms 节拍回报 `0xC7`，主机据此确认"写进去了"。

**这组 id 是台架工具，不是产品接口**：最大值 400‰（约 40 %）远高于这台减速电机的死区，但明显低于满转，脚本写错也不会让轮子突然满扭矩冲出去。

固件侧实现见 `firmware/app/02_Service/service_chassis/service_chassis.c` 的 `service_chassis_set_test_duty()`；主机侧封装见 `tools/bench/wheel_tune.py`。

### 5.5 存储与日志命令

> **实现状态：已实现。** 固件 `01_APP/app_robot/app_handlers.c` 处理 `0x08~0x0D`，所有 ACK 只表示"受理"，实际结果由 `0xC8 REPORT_STORAGE`（bit0 无脏数据 / bit3 最近一次保存失败）与 `0xC9` 的结束帧表达；Flash 操作全部在 `appStorage` 任务里执行，通信任务不会被擦除阻塞。实现细节见 [storage-design.md](storage-design.md) 第 12 节。分区、记录格式、掉电语义见 [flash-layout.md](flash-layout.md)，本节只定线上格式。

#### 5.5.1 PARAM_SAVE `0x08`

| 偏移 | 类型 | 字段 |
| --- | --- | --- |
| 0 | `uint8` | `scope`：0=参数区，1=标定区，2=全部 |

| 结果 | 条件 |
| --- | --- |
| `0x00` | 已受理，写入在后台进行 |
| `0x01` | `scope > 2` |
| `0x02` | `scope` 为 1 或 2 而底盘未失能（含急停） |
| `0x05` | 上一次存储操作尚未结束 |
| `0x06` | 外部 Flash 不可用 |

**"失能才允许写标定"**：改轮径、编码器比例、轮向会立刻改变里程计和逆解结果，行进中写入等于在运动中改尺子。参数区（PID、限速、超时）不要求失能——台架调参时底盘停着测，但允许例外。

#### 5.5.2 PARAM_RESET `0x09`

| 偏移 | 类型 | 字段 |
| --- | --- | --- |
| 0 | `uint8` | `scope`：0=参数区，1=标定区，2=全部 |
| 1 | `uint8` | `confirm`：必须为 `0xA5` |

恢复为 `app_robot_config.h` 的编译期值，**只改 RAM 并置脏，不自动落盘**——还要再发一次 `PARAM_SAVE` 才写进 Flash。这样"误按恢复"在断电前不会造成损失。

`scope` 为 1 或 2 时同样要求底盘失能；`confirm` 不符返回 `0x01`。

#### 5.5.3 STORAGE_QUERY `0x0A`

无负载。ACK `0x00` 之后立即发一帧 `0xC8 REPORT_STORAGE`。这是主机唯一需要轮询的存储接口，调参工具在 `PARAM_SAVE` 之后按 100 ms 间隔查 `storage_flags` 的 bit0，直到"无脏数据"才提示可以断电。

#### 5.5.4 LOG_EXPORT `0x0B`

| 偏移 | 类型 | 字段 |
| --- | --- | --- |
| 0 | `uint8` | `source`：0=运行日志环，1=故障事件环 |
| 1 | `uint8` | `action`：0=停止，1=开始 |
| 2 | `uint32` | `from_seq`：从该序号（含）开始；0=最旧一条 |

ACK `0x00` 受理后，MCU 以 `0xC9 REPORT_LOG` 逐条上报，**速率上限 20 Hz（50 ms 一条）**。上限是必须的：921600 波特率下一帧 64 B 约 0.7 ms，如果不限速，导出会把 `REPORT_WHEEL_SPEED` 和心跳挤掉，Host 会误判通信超时。导出期间故障记录照常写入，所以 `seq` 会增长，Host 按 `seq` 去重。

结束条件：到环尾（发一帧 `flags=0x02`、`text_len=0` 的结束帧）、收到 `action=0`、或链路断开 500 ms 自动停止。同一时间只允许一个导出；再次请求返回 `0x05`。

#### 5.5.5 REPORT_STORAGE `0xC8`（24 字节）

| 偏移 | 类型 | 字段 |
| --- | --- | --- |
| 0 | `uint8` | `storage_flags`，见下 |
| 1 | `uint8` | 日志等级 |
| 2 | `uint16` | 参数区当前 `seq` |
| 4 | `uint16` | 标定区当前 `seq` |
| 6 | `uint16` | 预留 |
| 8 | `uint32` | 累计启动次数 |
| 12 | `uint32` | 日志环已用字节 |
| 16 | `uint32` | 日志环累计擦除次数 |
| 20 | `uint32` | 上次成功保存时的开机秒数（0=从未保存） |

`storage_flags`：

| 位 | 含义 |
| --- | --- |
| 0 | **参数无脏数据**（全部已落盘）——主机据此判断能否断电 |
| 1 | 参数区有效（CRC 通过；否则上电用的是编译期默认值） |
| 2 | 标定区有效 |
| 3 | 最近一次保存失败 |
| 4 | 镜像槽 A 有效 |
| 5 | 镜像槽 B 有效 |
| 6 | 有未读的崩溃现场 |
| 7 | 日志环已回卷（最旧数据已被覆盖） |

发送时机：应答 `0x0A` 后一帧；每次保存结束（成功或失败）主动发一帧。**不做周期上报**——它没有周期性的信息量，每 10 Hz 挤进 `REPORT_STATUS` 只是浪费带宽。

#### 5.5.6 REPORT_LOG `0xC9`（15 + N，N ≤ 49）

| 偏移 | 类型 | 字段 |
| --- | --- | --- |
| 0 | `uint8` | `source`（同 `LOG_EXPORT`） |
| 1 | `uint8` | 等级 0~3 |
| 2 | `uint8` | `tag`：模块号（1=底盘 2=通信 3=机械臂 4=电源 5=急停 6=存储） |
| 3 | `uint8` | `flags`：bit0=还有更多，bit1=本次导出结束 |
| 4 | `uint32` | 时间戳（开机秒） |
| 8 | `uint32` | `seq` |
| 12 | `uint16` | 故障码（`source=1` 时有值，运行日志填 0） |
| 14 | `uint8` | `text_len` |
| 15 | `char[N]` | 文本，UTF-8/ASCII，无结尾 0 |

日志正文是文本而不是二进制：导出到 PC 后要能被 `grep`，排障时先用人眼读。故障事件环的 `text_len` 为 0，靠 `code` 区分——故障码是枚举，不需要文本。

#### 5.5.7 REPORT_CRASH `0xCA`（7 + N，N ≤ 57）

| 偏移 | 类型 | 字段 |
| --- | --- | --- |
| 0 | `uint8` | `slot`（0~15） |
| 1 | `uint8` | `flags`：bit0=还有后续分片 |
| 2 | `uint16` | 本分片在记录内的 `offset` |
| 4 | `uint16` | 记录总长 |
| 6 | `uint8` | 本片数据长度 |
| 7 | `uint8[N]` | 数据 |

一条崩溃记录约 1 KB，单帧放不下，所以按 offset 分片连续发送，Host 按 offset 拼接、按总长判定完整。`CRASH_READ` 的 `slot` 填 `0xFF` 表示最新有效槽。没有有效记录时 ACK 返回 `0x04`。

`CRASH_READ` 的 `flags` bit0 = 读完标记已读，对应 `0xC8` 的 bit6；`REPORT_CRASH` 的 `flags` bit0 = 本记录还有后续分片，两者不要混淆。**读取不清除记录**——崩溃现场是唯一的，主机解析确认后才发 `LOG_CLEAR`。

崩溃导出没有结束帧：主机按 `offset + total` 判定完成。收到 `LOG_EXPORT` 的 `action=0` 或链路静默 500 ms 时，固件同样会中止正在进行的崩溃导出，主机超时后可以重新发起。

#### 5.5.8 LOG_CLEAR `0x0D`

| 偏移 | 类型 | 字段 |
| --- | --- | --- |
| 0 | `uint8` | `source`：0=运行日志，1=故障事件，2=崩溃现场，3=全部 |
| 1 | `uint8` | `confirm`：必须为 `0xA5` |

后台擦除，ACK 只表示受理。清崩溃现场前先确认已经导出过——`0xC8` 的 bit6 只能说明"有未读"，说明不了"已备份"。

#### 5.5.9 互斥规则

- 同一时间**只允许一个存储写操作**（保存 / 恢复 / 清除 / 镜像写入），第二个返回 `0x05`。
- 日志导出与写操作互斥的只是"导出"这个动作本身：导出期间仍可记录新日志，两者在 Flash 上是不同区域。
- 保存请求优先于导出请求；导出进行中收到 `PARAM_SAVE` 时，导出继续，保存排队。

实现上 `0x05` 由 `PARAM_SAVE` 与 `PARAM_RESET` 返回（"上一笔保存未结束"）。`LOG_CLEAR` 只把扇区头写成 0，不碰参数/标定区，请求入队后由存储任务串行执行，因此不参与这条互斥。

## 6. CRC16

**算法**：CRC-16/CCITT-FALSE

| 参数 | 值 |
| --- | --- |
| 多项式 | `0x1021` |
| 初值 | `0xFFFF` |
| 输入反射 | 否 |
| 输出反射 | 否 |
| 结果异或 | `0x0000` |
| 校验值 | 对 ASCII `"123456789"` 计算结果为 **`0x29B1`** |

**计算范围**：从 `LEN` 字节开始，到 `PAYLOAD` 最后一个字节（含）。**不含帧头，不含 CRC 自身。**

### 参考实现（C，逐位法，够快且不占表空间）

```c
uint16_t crc16_ccitt(const uint8_t *data, uint16_t len)
{
    uint16_t crc = 0xFFFF;
    for (uint16_t i = 0; i < len; i++) {
        crc ^= (uint16_t)data[i] << 8;
        for (uint8_t b = 0; b < 8; b++) {
            if (crc & 0x8000)
                crc = (uint16_t)((crc << 1) ^ 0x1021);
            else
                crc = (uint16_t)(crc << 1);
        }
    }
    return crc;
}
```

### 参考实现（Python，用于 PC 端单元测试和对拍）

```python
def crc16_ccitt(data: bytes) -> int:
    crc = 0xFFFF
    for byte in data:
        crc ^= byte << 8
        for _ in range(8):
            crc = ((crc << 1) ^ 0x1021) & 0xFFFF if crc & 0x8000 else (crc << 1) & 0xFFFF
    return crc
```

**两面必须用同一份实现验证过测试向量**（见第 10 节）再联调。CRC 对不上是联调第一大坑，先把这一步单独验证掉。

## 7. 通信时序与超时

| 项目 | 值 | 说明 |
| --- | --- | --- |
| 速度指令周期 | 20 ms | Host 每 20 ms 发一帧 SET_VELOCITY |
| 控制指令超时 | **200 ms** | MCU 超过此时长未收到有效 SET_VELOCITY → **主动停车** |
| 关键命令 ACK 超时 | 200 ms | 未收到应答则重发 |
| 重发次数上限 | 3 次 | 超过则上报 `0x0202` |
| 心跳周期 | 100 ms | MCU → Host |
| Host 心跳超时 | 500 ms | 判定 MCU 失联 |
| CRC 连续错误阈值 | 10 帧 | 触发上报 `0x0201` |
| 参数保存耗时 | 典型 < 100 ms，最大 500 ms | 4 KB 扇区擦除 45 ms 典型 / 400 ms 最大，加页编程与回读校验 |
| 日志导出速率 | ≤ 20 Hz | 见 5.5.4，限速是为了不挤掉速度帧与心跳 |

### 超时停车的设计理由

控制指令断流有几种可能：Host 崩溃、进程卡死、线断了、ROS 节点被 kill。**没有任何一种情况下机器人应该继续沿最后一条速度指令跑下去。** 所以"收不到新指令就停车"是必须的，不能靠 Host 主动发停车指令——Host 正是可能出问题的那一端。

200 ms 是权衡：太短（如 50 ms）会因为一次丢帧误触发，太长则失控距离过大（0.5 m/s × 0.2 s = 10 cm）。

## 8. 故障码

| 码 | 名称 | 级别 | 处理 |
| --- | --- | --- | --- |
| `0x0101` | 电机过流 | ERROR | 该轮停止，上报 |
| `0x0102` | 编码器异常（跳变/长时间无变化） | ERROR | 该轮停止，上报 |
| `0x0201` | CRC 错误率超限 | WARN | 上报，不停止 |
| `0x0202` | 通信超时 | FATAL | **立即停车**，上报 |
| `0x0301` | 关节超限位 | ERROR | 该关节停止 |
| `0x0302` | 关节堵转（电流超限且位置不变） | ERROR | 该关节停止 |
| `0x0303` | 轨迹执行异常 | ERROR | 停止机械臂 |
| `0x0401` | 电池低压 | WARN | 上报，禁止新任务 |
| `0x0402` | 温度过高 | WARN | 上报，降额运行 |
| `0x0501` | 急停触发 | FATAL | 全停 |
| `0x0601` | 参数区无效（CRC 失败/空白/版本不兼容） | WARN | 用编译期初值运行，参数置"未固化" |
| `0x0602` | 标定区无效 | WARN | 用编译期标定运行，里程计精度不受保证 |
| `0x0603` | 存储写入失败（擦除/编程/回读校验不符） | ERROR | 停止保存与升级，运行继续 |
| `0x0604` | 分区表或镜像槽无效 | ERROR | 退回编译期分区表；禁用外部镜像升级 |

**级别定义**：

- **WARN**：记录 + 上报，系统继续运行但受限制
- **ERROR**：停止对应子系统，其他部分继续（如机械臂故障不影响底盘移动）
- **FATAL**：全部停止，必须人工清除

故障码只置位不清零，直到 Host 发 `CLEAR_FAULT` 且条件已消失。**条件没消失时拒绝清除并返回 `0x02`**——否则会出现"清了又立刻报"的抖动。

`REPORT_STATUS` 只带一个故障码。多个条件同时成立时按上表的级别仲裁：**级别高的顶替级别低的，同级保留先锁存的那个**（急停是显式强制覆盖）。所以一个 `0x0401`（WARN）不会挡住随之而来的 `0x0202`（FATAL）——被顶替的条件若仍然存在，会在下一次 `CLEAR_FAULT` 之后重新上报。

## 9. 接收解析

解析器的**行为**是协议的一部分，具体写法可以不同。

**必须满足**：

1. **与切分无关**：必须能处理任意分块（1 字节、整帧、半帧粘包都行），不能假设一次读到完整帧。
2. **先校验 LEN 再取负载**，LEN 不在 `[2, 66]` 时丢弃，不能越界。
3. **CRC 不符只丢弃这一帧**，然后继续找下一帧，不能停摆、不能崩溃。
4. **负载里的 `AA 55` 不能造成错位**：帧边界只由 LEN 决定，不能一看到帧头就当新帧开始累加。
5. **50 ms 复位**：两个字节间隔超过 50 ms 时，丢弃半帧重新同步（比如收到一半线断了）。
6. 错误帧率高时只上报（`0x0201`），不断开连接。

**本固件的实现**（`05_Middlewares/protocol/protocol_codec.c`）：

- 71 字节重组缓冲区。每次 `feed()` 把新字节追加进缓冲区，然后从头扫描：找到 `AA 55` 且 LEN 合法时，一次性计算 CRC 并取出整帧。
- 任何一步失败只**丢 1 个字节再重新扫描**，所以不需要维护"当前在哪个状态"，也不会被负载里的伪帧头带偏。
- 代价是异常时会对同一段字节重复扫描几遍；帧长 ≤ 71 B、115200 波特率下最多约 10 KB/s，这点开销可以忽略，换来的是唯一的错误路径。
- "最后收到字节的时间"由 `service_proto` 传入，用于 50 ms 复位；解析器本身不读时钟。

**分层位置**：

| 位置 | 负责 |
| --- | --- |
| `05_Middlewares/protocol` | 协议表（命令字、负载长度、结果码、故障码）、组帧/解帧、CRC、字段读写。纯 C，不依赖 HAL/FreeRTOS，可在 PC 上单测 |
| `02_Service/service_proto` | 从 DMA 环形缓冲取字节喂给解析器、分发命令、生成 ACK、SEQ 去重、组上报帧、链路统计 |
| `01_APP/app_robot` | 注册每条命令的处理函数，把服务调用翻译成业务动作；按周期决定何时上报 |

把解析放在 service 而不是 app 的理由：解析和应答是**协议的实现**，不是业务逻辑。放在 service 里，换一个应用仍然复用同一套通信行为；app 只关心"收到 SET_ENABLE 该干什么"，可以用直接调用处理函数的方式做单元测试，不需要构造字节流。

### 关于 SEQ 去重

- 对 `SET_VELOCITY`：**不需要去重**。重复执行同一条速度指令无害。
- 对 `SET_ENABLE` / `SET_PARAM`：**必须去重**。记一个"已执行的最大 SEQ"，重复的直接回 ACK 但不执行——否则一次重传会导致参数写两遍 Flash（虽然结果相同，但磨损和耗时都不必要）。
- 对 `PARAM_SAVE` / `PARAM_RESET` / `LOG_CLEAR`：**必须去重**。这几个是 Flash 擦写，重传会造成双倍磨损；而且 `PARAM_RESET` 重放会把刚改好的参数再清一次。
- 对 `LOG_EXPORT` / `CRASH_READ` / `STORAGE_QUERY`：**不需要去重**，但导出重复请求会被 `0x05`（忙）挡住，天然幂等。
